# AGENTS.md

Guidance for AI agents and new contributors working in this repository. Read this before making changes. Where this file and `docs/architecture.md` disagree, trust the code: `architecture.md` captures the original v1 plan, and the as-built has moved on (admin-post handlers plus a REST API instead of admin-ajax, and added TLS and email-DNS checks).

## What this is

Domain Monitor is a WordPress plugin (PHP, namespaced PSR-4 under `DomainMonitor\`) that monitors domain health: RDAP registration/expiry, DNS, TLS certificate, email DNS, and www/apex policy. It stores state in custom tables and surfaces status through an admin dashboard widget, an admin page, a read-only REST API, and WP-CLI. There are no external API keys; checks hit public RDAP, DNS, and HTTP endpoints only.

## Ground rules

- **PHP 7.4 is the floor.** Shipped code must run on PHP 7.4. No constructor property promotion, `match()`, enums, named arguments, or the nullsafe operator. CI runs the suite on 7.4 through 8.3 and all must stay green. (A past regression shipped an accidental PHP 8.0 `match()`; use array lookups or `switch` instead.)
- **WordPress conventions and security are non-negotiable.** Capability check plus nonce on every mutation, `$wpdb->prepare()` for all variable SQL, late escaping on output, strict input sanitization.
- **Test-first.** There are ~38 PHPUnit classes under `tests/Unit` (Yoast PHPUnit Polyfills). Add or adjust tests alongside behavior changes.
- **Keep WordPress out of the core logic.** Domain logic lives in plain classes that receive their collaborators by injection. WordPress specifics (hooks, `$wpdb`, `wp_remote_get()`, cron, options) belong in thin adapters. This is what lets the unit tests run without booting WordPress; preserve the seam.

## Repository map

- `domain-monitor.php` — bootstrap: constants, autoload, activation/deactivation hooks, `plugins_loaded` boot of `Plugin`, WP-CLI registration, and the guarded self-updater.
- `src/Plugin.php` — wires every hook: cron, REST (`rest_api_init`), admin menu, dashboard widget, `admin_post_*` form handlers, admin notices.
- `src/Checks/` — one checker per concern: `RdapChecker`, `DnsChecker` (+ `NativeDnsResolver`), `SslChecker` (+ `CertificateFetcher`/`StreamCertificateFetcher`), `EmailDnsChecker`, `WordPressHttpClient`, plus `*Result` value objects. `CheckRunner`/`DomainCheckRunner` orchestrate a full per-domain check.
- `src/Domain/` — primitives: `DomainName`, `ApexDomain`, `MonitorableHost` (the localhost/dev guard), `ExpirationDate`, `DomainStatus`, `StatusCalculator`, and the bundled public suffix list at `data/public-suffix-list.php` (regenerated by `bin/generate-psl.php`).
- `src/Storage/` — `DomainStore`/`AlertStore` interfaces with `Array*` (in-memory, tests) and `Wpdb*` (production) implementations; `DomainRepository`, `DomainRecord`, `DomainTable` (table-name resolver), `Installer` (schema + `maybeUpgrade`).
- `src/Diff/` — `SnapshotDiffer`/`SnapshotDiff` for drift detection between snapshots.
- `src/Alerts/`, `src/Notifications/` — alert lifecycle (`AlertResolver`) and admin notices.
- `src/Rest/StatusController.php` — `domain-monitor/v1` read-only status (`/status`, `/status/{domain}`), permission via the `domain_monitor_rest_permission` filter.
- `src/Cli/` — the `wp domain-monitor` command and its printers.
- `src/Settings/PluginSettings.php` — options-backed settings.
- `tests/` — PHPUnit; `tests/Unit` mirrors `src/`.
- `bin/` — `build.sh` (release packaging), `smoke-test.sh` (wp-env behavioral test), `generate-psl.php`.
- `docs/` — `architecture.md`, `v1-spec.md`, `test-plan.md`.

## Data and names

- Tables: `{prefix}domainmon_domains`, `{prefix}domainmon_alerts`. Always resolve names through `DomainTable`; never hardcode them.
- Schema version and settings live in WordPress options (e.g. `domain_monitor_schema_version`).
- Cron hook: `domain_monitor_daily_check` (daily). Each domain check is isolated so one failure cannot abort the batch.
- On activation the plugin auto-detects the site host (guarded against `localhost`/dev hosts by `MonitorableHost`) and honors the `DOMAIN_MONITOR_PRIMARY_DOMAIN` constant override.
- `uninstall.php` is multisite-aware: it drops tables and clears options for every site.

## Commands

```bash
# Unit tests (Docker/wp-env)
npm install && npm run wp-env:start && npm run wp-env:composer && npm run test:unit

# Unit tests (local PHP/Composer)
composer install && composer test

# Behavioral smoke test (needs wp-env running)
bash bin/smoke-test.sh

# Build a release zip
bin/build.sh [--with-updater] [--keep-staging]
```

## Build and release

- `bin/build.sh` exports from `HEAD` via `git archive`, so **commit before building**. It refuses a dirty tree (override with `ALLOW_DIRTY=1`) and aborts if the plugin header `Version` and `DOMAIN_MONITOR_VERSION` disagree.
- **Version is single-sourced** from the plugin header. Bump the header and the constant together; they must match.
- **Two channels:**
  - Default = WordPress.org-clean. No self-updater. This is the artifact destined for the .org repo.
  - `--with-updater` = GitHub dogfood. Bundles `yahnis-elsts/plugin-update-checker` via a dynamic `composer require` into the staging copy only. **Never add this package to the committed `composer.json`:** it must stay out of the default build, and WordPress.org forbids bundled updaters.
- The bootstrap activates the updater only behind a `class_exists` guard, so leaving that code in place is safe for the .org build.
- `composer require` uses `--update-no-dev` (not `--no-dev`, which is install-only). The release workflow dry-runs both composer commands before building to catch a bad invocation early.
- The build verifies its output: it fails if any dev path leaks in, or if the updater is present in the clean build / missing from the dogfood build. If you add a new top-level dev artifact, add it to the prune list in `bin/build.sh`.
- `enableReleaseAssets()` in the updater bootstrap is required: GitHub's source zipball lacks `vendor/`, so updates must use the built release asset (`domain-monitor-<version>.zip`).

### Cutting a release

1. Bump the version in both the plugin header and `DOMAIN_MONITOR_VERSION`.
2. Commit.
3. Tag `vX.Y.Z` and push the tag. CI builds the dogfood zip and attaches it to the GitHub release.
